# Поиск горячих билетов из Ташкента: дизайн

## Цель

Сделать каталог Telegram-бота понятным обычному пользователю: все рейсы отправляются из Ташкента, направления можно искать по русскому названию или IATA-коду, а весь доступный каталог можно просматривать страницами. Origin и currency являются системными константами `TAS/UZS`; пользователь управляет только фильтрами класса перелёта и багажа.

## Границы задачи

В задачу входят:

- фиксированные origin `TAS` и currency `UZS`;
- синхронизация Explore API только с query-параметрами `origin` и `currency`;
- сохранение класса перелёта и признака багажа из ответа API;
- поиск destination по IATA-коду или русскому названию из `IATA_LOCATIONS_RU`;
- читаемые названия локаций во всех пользовательских сообщениях;
- постраничный просмотр всех активных горячих билетов;
- фильтрация выдачи и уведомлений по пользовательским настройкам класса и багажа.

Не входят:

- изменение origin или currency пользователем;
- отдельная синхронизация под настройки каждого пользователя;
- fuzzy-поиск с исправлением опечаток;
- многоязычные справочники;
- изменение расписания cron или VDS-архитектуры.

## Системные константы

В application/domain слое вводятся единые константы:

```text
DEFAULT_ORIGIN_CODE = TAS
DEFAULT_CURRENCY_CODE = UZS
TICKET_PAGE_SIZE = 10
```

Ни один пользовательский flow не принимает origin или currency. Существующие поля SQLite сохраняются для совместимости с текущими repository contracts, но новая миграция приводит все записи пользователей и подписок к `TAS/UZS`.

## Синхронизация Aviasales

Запрос строится строго так:

```text
GET /v1/hot_offers/list.json?origin=TAS&currency=uzs
```

Параметры `trip_class`, `with_baggage`, `direct`, `language`, `market` и остальные прежние фильтры в запрос не передаются. Sync остаётся общим для всех пользователей и обрабатывает единственный enabled source `TAS/UZS`.

Mapper извлекает из каждого предложения:

- `trip_class` и приводит `1` к `economy`, `2` к `business`;
- `with_baggage` в `hasBaggage`;
- остальные существующие поля билета.

Предложения с неизвестным `trip_class` пропускаются из каталога с событием `aviasales_offer_mapping_failed`; raw payload или внутренние детали не отправляются пользователю.

External key должен различать предложения разных классов, чтобы эконом и бизнес одного маршрута не перезаписывали друг друга.

## IATA-справочник

`src/constants/iata-locations-ru.ts` является источником кода, города, страны и русских названий. Domain helper предоставляет три операции:

1. `formatLocationLabel(code)` возвращает `Ташкент (TAS)`; неизвестный код возвращает как есть.
2. `resolveLocation(input)` принимает точный IATA-код либо точное русское `name`/`cityName` без учёта регистра и лишних пробелов.
3. При нескольких совпадениях предпочтение получает запись, у которой `code === cityCode`. Если однозначный city code выбрать нельзя, helper возвращает варианты, а бот просит пользователя ввести точный IATA-код.

Опечатки автоматически не исправляются. Для неизвестного текста бот отвечает: `Город не найден. Введите название или IATA-код, например Стамбул или IST.`

Во всех пользовательских сообщениях используется формат:

```text
Ташкент (TAS) → Стамбул (IST)
```

Это относится к карточкам билетов, Telegram-уведомлениям, списку подписок, профилю, настройкам и поисковым подсказкам.

## Пользовательский flow горячих билетов

### Начало поиска

Кнопка `🔥 Горящие билеты` и команда `/tickets` без аргумента создают session flow `ticket_search` и отправляют:

```text
Вылет из Ташкента (TAS). Куда летим?
```

Сообщение содержит кнопку `🌍 Все направления из Ташкента`. Пользователь также может ввести название города или IATA-код.

Команда `/tickets IST` обходит вопрос, разрешает `IST` через тот же helper и сразу открывает первую страницу.

### Пагинация

Ticket repository принимает `limit` и `offset`. Application service запрашивает `TICKET_PAGE_SIZE + 1`, отправляет первые десять записей и использует одиннадцатую только как признак следующей страницы.

Порядок страниц стабилен: сначала цена по возрастанию, затем дата вылета и database id. Одинаковый билет не должен перескакивать между страницами при неизменном каталоге.

После карточек бот отправляет навигационное сообщение:

```text
Показано 1–10
```

Возможные inline-кнопки:

- `⬅️ Назад`, если offset больше нуля;
- `➡️ Показать ещё`, если была получена одиннадцатая запись.

Callback содержит только короткие значения destination (`IST` или `ALL`), offset и компактную сигнатуру фильтра (`E0`, `E1`, `B0` или `B1`). При обработке бот использует Telegram user id из callback, заново загружает настройки пользователя и проверяет границы offset. Callback другого пользователя не может читать состояние или настройки владельца исходного сообщения.

В режиме `ALL` destination-фильтр отсутствует. Таким образом, пользователь может пройти весь активный каталог `TAS/UZS`, а не только первые пять записей. Выдача включает только активные билеты с датой вылета не раньше текущей даты в `Asia/Tashkent`.

## Настройки пользователя

Origin и currency удаляются из settings flow. Остаются два параметра:

- `Класс перелёта`: `Эконом` или `Бизнес`;
- `Багаж`: `Не важно` или `Только с багажом`.

Значения по умолчанию:

```text
tripClass = economy
baggageRequired = false
```

Настройки хранятся в таблице `users`. Их изменение немедленно влияет на выдачу горячих билетов и на все активные уведомления пользователя. Синхронизацию эти настройки не изменяют.

Профиль показывает:

```text
Город вылета: Ташкент (TAS)
Валюта: UZS
Класс: Эконом
Багаж: Не важно
```

## Уведомления

Создание уведомления больше не спрашивает origin и currency. Flow начинается с destination; сохранённая подписка всегда получает `TAS/UZS`.

Базовые критерии подписки остаются: destination, диапазон дат, максимальная цена и прямой рейс. Перед отправкой notification service дополнительно сравнивает билет с текущими настройками владельца:

- `ticket.tripClass === user.tripClass`;
- если `user.baggageRequired`, то `ticket.hasBaggage` должен быть `true`.

Изменение настроек применяется динамически ко всем активным подпискам; копировать класс и багаж в каждую подписку не требуется. Дедупликация по пользователю, подписке, билету и цене сохраняется.

Существующее поле `subscriptions.baggage_required` остаётся только для совместимости schema, сбрасывается в `0` миграцией и больше не является источником пользовательской настройки.

## Изменения данных

Новая SQLite-миграция:

- добавляет `users.preferred_trip_class` с default `economy` и CHECK для `economy/business`;
- добавляет `users.baggage_required` с default `0`;
- добавляет `tickets.trip_class` с CHECK для `economy/business`;
- обновляет всех пользователей: `default_origin_code = 'TAS'`, `preferred_currency_code = 'UZS'`;
- обновляет все подписки: `origin_code = 'TAS'`, `currency_code = 'UZS'`, `baggage_required = 0`;
- отключает другие sync sources и гарантирует enabled source `TAS/UZS`.

Существующие ticket rows не имеют достоверного класса. Миграция помечает их как `economy`, поскольку текущая версия синхронизировалась с `trip_class=Y`. Следующий sync обновляет каталог данными из нового двухпараметрового запроса.

## Ошибки и безопасное поведение

- неизвестная локация не завершает polling и приводит к пользовательской подсказке;
- неизвестный IATA в сохранённом билете отображается исходным кодом;
- пустая страница сообщает `Подходящие билеты не найдены`;
- offset меньше нуля, нецелый или слишком большой отклоняется callback-ответом;
- malformed callback не раскрывает внутренние ошибки;
- если текущая сигнатура настроек не совпадает с callback, следующая страница строится по новым настройкам с offset `0`, чтобы не пропустить или не повторить элементы;
- Telegram token и raw payload не попадают в пользовательские сообщения или error logs.

## Тестирование

### Unit

- URL содержит ровно `origin=TAS` и `currency=uzs`;
- mapper нормализует `trip_class` и `with_baggage`;
- location resolver работает для `IST`, `Стамбул`, регистра, пробелов, неоднозначных и неизвестных значений;
- formatter возвращает читаемую подпись и fallback для неизвестного кода;
- pagination корректно вычисляет предыдущую и следующую страницы.

### Integration

- migration приводит legacy users/subscriptions/sources к `TAS/UZS`;
- настройки фильтруют список по классу и багажу;
- страницы по десять позволяют получить весь набор без дубликатов и пропусков;
- `ALL` показывает все направления, destination показывает только выбранное;
- menu button и `/tickets` запускают поиск, `/tickets IST` открывает результат;
- создание подписки не запрашивает origin/currency;
- notification matching учитывает текущие пользовательские настройки;
- все Telegram presenters используют читаемые названия.

### Полная проверка

`npm run verify` должен пройти ESLint, strict TypeScript, весь Vitest-набор и production build.

## Развёртывание

Архитектура VDS не меняется. После доставки кода выполняются build и restart systemd service. Cron продолжает запускать общий sync каждые десять минут. Миграции применяются автоматически при старте бота или ручном sync.
